# VALIDATIONS — single-node model test against a representative pattern set

Validation of the single-node model (`docs/ARCHITECTURE.md`) on 2026-08-27,
using a **fictitious in-repo domain** only. No consumer patterns, names or data
live in this repository (see AGENTS.md rule 7). The pattern shapes exercised
here are representative of composite patterns in general.

## Setup

One node serving a full roster locally: several `main` patterns (starting
agents) + one tool + several linguistic atomics + composites (sequence /
parallel) + the inline parallels generated by the mains. Each agent = one queue
+ one pool; one beaver; API + mini-manager.

## Traces

### `main_a` (smallest main)

`[tool_extract → parallel [summ, cata, keys]]`

1. **API** `submit(main_a, {payload})` → `task_id T`, inputs staged, root token
   `[main_a]`, `root=True`, `ultimate_return=client:T` → queue `main_a`.
2. **main_a** (sequence, index 0) deposits to `tool_extract` (tool). Result
   `{text, lang}` returns to main_a's dual queue.
3. index 1 → parallel inline → deposit to `main_a_processors` (its own dual
   queue + call-frame) with the DAG `[summ, cata, keys]`.
4. Fan-out to the 3 queues; each child returns to `main_a_processors`;
   **fan-in dedupe by DAG path, scoped per (parallel agent, task_id)**.
5. **Merge = flat union** `{summary, cats, keys}` → main_a accumulates
   flat `{text, lang, summary, cats, keys}` → final index → delivery to
   `client:T` (results board).

### `main_b` (heavier main, nested composite)

`[tool_extract → parallel [summ, cata, keys, goal, draft_flow]]`

1. Same until the parallel fan-out, which includes `draft_flow`
   (sequence `[outline_step → inline-linguistic draft]`).
2. `draft_flow`: step 0 `outline_step` with `output_as: stage_b`;
   step 1 is an **inline linguistic stage** (prompt embedded, unnamed) that
   reads `input.payload` and `stage_b.outline`.
3. Everything converges: parallel merges `{draft}` with the rest → sequence
   joins it with `{text, lang}` → client.

### Result without structural changes, but with four concrete refinements

The model (dual queues, root token, per-task boards, pools over shared
atomics, delegation) validates this representative set on one node. The
pattern set forces four contract-level refinements — H1–H4.

## Refinements surfaced (H1–H4)

- **H1. Inline stages.** Realistic YAML uses unnamed stages with embedded
  prompts (linguistic) and named inline parallels (`main_a_processors`).
  Contract: *inline parallel → auto-named agent* (own queue + join);
  *inline linguistic → self-executed by the owning composite* (no
  intermediate queue). Moved into LEG-010.
- **H2. Dotted template paths + system vars.** Prompts use `{input.payload}`,
  `{stage_b.outline}`, `{input.lang}`, `{current_date}`. Contract: the
  blackboard is **composite-scoped** (nested `input`, `stage_b`, …) and
  the templating engine resolves dotted paths plus system variables (e.g.
  `current_date`). Without this the prompts cannot be filled. Moved into
  LEG-010.
- **H3. Merge semantics.** A composite merges children without collisions; a
  child can emit *two* keys (`persons`, `companies`); sequences accumulate
  flat. Contract: merge = **flat union of child outputs**, rename via
  `output_as` when keys collide; sequences accumulate flat. Moved into
  LEG-010.
- **H4. Schema compilation.** `output_schema` needs unions (`["string","null"]`),
  arrays, nested objects and recursion (`outline`). Compiled to pydantic with
  deferred refs; validated at the queue boundary. Moved into LEG-010.

## What the traces confirm

- **Two `B`s = two tasks**: every occurrence of a shared pattern is a distinct
  `task_id` + DAG path; per-task boards (`blackboard:{node}:{task_id}`) prevent
  cross-talk (concurrent runs of the shared atomics).
- **Dual-queue fan-in works** for both sequence and parallel when the DAG path
  (not the agent name) is the dedupe key.
- **Pools over shared queues**: the tool and the shared atomics are natural
  pool points on a single node.
- **Root token semantics** (final derived from position, delivery to
  `client:{task_id}`) hold for all `main` patterns.

## Status

Model validated on a single node against a representative (fictitious, in-repo)
pattern set. H1–H4 are acceptance criteria for LEG-010 (patterns v1). A
follow-up adds these two patterns as YAML v1 conformance fixtures.
