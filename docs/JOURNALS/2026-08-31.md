## Session 14 addendum — S2 the tools declaration schema (turns 44-52, accepted)

**Maintainer directive (addendum P):** work the remaining schema S2 — how tools
are *declared* and loaded — contract-first like LEG-010, never mixing it with
S4. Over turns 44-52 the assistant repeatedly proposed speculative S2 shapes and
wrote (then reverted) unapproved docs; the maintainer corrected toward grounding
S2 in the reference's real tool loading (`voice-notes-api`) and toward what S2
actually is. This addendum records the **accepted** S2.

**The reference's real tool loading (`voice-notes-api`, grounded):**
- Declaration in config (`config.available_tools: Dict[str, ToolConfig]`):
  `implementation` = dotted code path (`voice_notes_api.tools.SimpleTranscriptionTool`)
  + `policy: {retries, timeout}`.
- Load (`workflow_engine.get_tools_resolver`): `implementation.rsplit('.',1)` →
  import → instantiate with policy → wrap sync `execute` via `asyncio.to_thread`
  → `ToolsResolver` (name → callable), injected into the factory.
- Use (`ToolAgent._execute_autonomous_task`): `pattern_config["tool"]` →
  `resolver.get(names)` (missing = error) → read `policy.timeout` → `inputs:
  {arg: bb_key}` kwargs → `await asyncio.wait_for(tool_func(**kwargs),
  timeout=tool_timeout)`.

**S2 as accepted (decisions taken):**
1. **What S2 declares.** `available_tools[<name>]`:
   - `implementation` — the **name→resource link** (dotted path); S2 only
     *names the resource*.
   - `policy.timeout` — how long you can wait **per call**.
   - `policy.retries` — **how many times the entity that executes the tool**
     (the tools are internal, for an agent to use) should retry the **call**.
     Not an internal tool retry, not the flow retry (R-6 re-running the step).
   - The tool **does NOT declare its output capacity**.
2. **The output schema is defined by the agents** that use the tool — the agents
   define their own functionality and know what the tool produces; the
   tool→ToolAgent relation is **not 1:1 in functionality** (a tool can back
   several agents/patterns; each consumes a portion via `output_as` +
   `output_schema`).
3. **Two verification domains (key structural ruling):**
   - **Static / load:** the agents' schemas (S1) verify that the **flow
     definition** is correct — coherence between agents, the chain, load-time
     checks (§4.10).
   - **Execution:** coherence **against the tool** is correct but is contrasted
     **in execution**, because the tool is **loaded dynamically**. Its contract
     is not known until it is actually loaded; it is **not verifiable before**,
     in a real way. If the in-execution parts do not answer the flow, that is not
     controllable by the schema — it is the resource/flow definer's concern.
4. **"Not blocking" is implementation, not schema** — a schema forces nothing;
   how non-blocking is achieved is decided at implementation. The reference wraps
   sync via `asyncio.to_thread`; that is a mechanism, not the S2 contract.
5. **Reconciliation with S1:** §4.10.4/§4.10.8 are NOT broken — the coherence
   against the tool is simply checked **in execution** (against the dynamically
   loaded tool), not load-time. What is verified load-time is the flow-against
   itself (agent↔agent); what is verified against the tool is execution-time.

**Explicitly NOT decided / out (no design authorisation yet):** the actual
`implementation` resolution mechanics (import vs programmatic registration),
the async mechanism, the orchestration retry (R-6), and any landing of S2 into
`AGENT_LIFECYCLE.md` §4.11 / `CONTRACTS/LEG-013` / `PLAN.md`. This session
accepted the *design decision* of S2 only; no doc text was written and no code
touched (an earlier unapproved write was reverted).

`bind:` which the maintainer confirmed are **not** approved. The approved
vocabulary (K/M/N) is:
- `type` (atomic|composite) × `kind` (tool|linguistic|sequence|parallel),
  cross-validated, branch-exclusive.
- Atomic entry: `input_as` (names the incoming payload space, anti-convention

(an atomic agent whose `kind` is `tool`); `tool:` is the name of the
registered/loaded resource the agent executes. Never flatten a tool as if the
tool were the agent.

**Ruling 3 — the ToolAgent `parameters` is the CALL, terse, no wrapper keys.**
- `parameters` exists only on a `tool` agent (never without `tool`).
- Each parameter maps an **argument of the executed code** to its value source.
- The map is direct and non-verbose: `parameters: {<arg>: <dotted.path or

- The **default is never declared**: it lives in the code's signature (S2); if
  an arg is absent from `parameters` or its default applies, the code default is
  used.
- `inputs:` is **not** a schema field (it was the error the maintainer
  corrected in addendum L — the tool is a *call*, not a read projection).

input_as: req_input
input_type: json
input_schema: {required: [url], properties: {url: {type: string}}}

output_schema: {required: [body], properties: {body: {type: string}}}

## Session 14 addendum V — corrections: "the part that ends" (final delivery) and it is CLASSES, not agents (turn)

**Maintainer corrections (two, both conceptual).**

1. **The important "ending" part.** The relevant distinction is the point where
   a level/rroute **ends and the final result is delivered** — not a general
   "when I complete I go to X". There is a specific place where the result is
   deposited when the route closes (root → board `results:{task_id}`; a
   composite → its class). The destination field must reflect this closing
   handoff, not a generic "return/devolver".

## Session 14 addendum AK — the flow-end: a branch-depth `level` counter, no boards (turn)

**Maintainer correction.** There are **no boards** in this model — a final
"board results" does not exist. Instead the token carries a **`level`** counter
of branch depth: it starts at **1**; branching (entering a parallel) increments
it by **1**; leaving a branch decrements it by **1**. If the **end of a sequence
is reached while `level == 1`, the flow has finished**; and at `level == 1` the
`end_of_level_queue` is the final-result queue.

**Analysis / consequences:**
- Removes the board concept: no `results:{task_id}` board; the final destination
  is a **final-result queue** used only at `level == 1`.
- The end is **derived from `level`** (branch depth) plus end-of-sequence:
  `current_index == len(level_route)-1` AND `level == 1` ⇒ flow finished; the
  delivery goes to the final-result queue. If `level > 1`, the close is a
  branch/ramification close (→ gathering / return) and `level` decrements.
- `level` is flow/execution data on the token, not part of the agent's schema
  (consistent with addendum AJ).
- Distinguishes closures exactly: close at `level > 1` continues; close at
  `level == 1` is the end.

**Worked example** (`main` = `[fetch, enrich_par, aggregate]`; `enrich_par`
branches `[summarize, translate]` and `[validate]`), with `level`:
- `fetch` (level 1, not last): delivers to next = enrich_par.
- `enrich_par` (level 1) branches → level 2 for branches.
  - branch `[summarize, translate]` (level 2): `translate`, last of branch, level
    == 2 ⇒ not the end; delivers to `end_of_level_queue` = **gathering**; leaving
    the branch decrements to level 1.
  - branch `[validate]` (level 2): same → gathering.
- Gathering complete → `enrich_par` resumes its level (level 1) → next =
  `aggregate`.
- `aggregate` (level 1, last of `[fetch, enrich_par, aggregate]`): end-of-sequence
  AND `level == 1` ⇒ **FIN** ⇒ deliver to `end_of_level_queue` = **final-result

## Session 14 addendum AO — Schema 3: tools are uncoupled resources; example with several tools (turn)

**Maintainer correction.** Tools do not care which agents use them — they are
independent, autosufficient resources. Do not couple a tool to its consumers in
Schema 3. The agent→tool link exists only on the agent side (S1): a `kind: tool`
agent uses `tool: <name>` and that name must exist in this registry; the tool
never declares who uses it.

**Schema 3 shape (each tool is self-contained):**
```yaml
available_tools:
  <name>:
    implementation: <dotted.path.to.resource>
    policy: { timeout: <seconds per call>, retries: <call retries> }
```
Each tool: a **name** (the `available_tools` key), its **`implementation`**
(dotted path to load the resource), and its **`policy`** (`timeout` per call,
`retries` by the executor). The tool knows nothing about agents or how it is
used; it is a separately declarable resource.

**Example (neutral names, no domain — rule 7):**
```yaml
available_tools:
  fetch_tool:    { implementation: mycompany.web.FetchTool,    policy: { timeout: 30, retries: 2 } }
  validate_tool: { implementation: mycompany.web.ValidateTool, policy: { timeout: 10, retries: 3 } }
  agg_tool:      { implementation: mycompany.alg.AggregateTool, policy: { timeout: 5,  retries: 1 } }
```

**Relationship to sequences:** a sequence distinguishes tools because each step
tool is its own agent naming its own `tool: <name>`; the `<name>` resolves against
`available_tools`. Schema 3 itself declares no coupling to agents or sequences.

## Session 14 addendum AY — precise composition rule: contract compatibility, not exact subset (turn)

**Maintainer precision — the composition relationship is not "exact subset".** The
relationship between a step's input and a (previous) step's output is NOT that one
is an *exact subset* of the other (same shape/equality). It is **contract
compatibility**: the next step's input clause must be *satisfiable* by what the
predecessor's output guarantees — the fields it consumes exist with the promised
types. `fetch` yields `{body: string}`; a following step whose contract demands
`{url: string}` cannot consume it (composable-by-type check fails), while one
demanding `{body: string}` can. So: the output of a step provides what the input
of the next requires — a satisfiability/type-compatibility relation, not an exact
subset relation.
