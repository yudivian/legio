## Design session (agent lifecycle, session x)` · consolidated model: Runtime / Registry / TaskManager

**Trigger.** Analysis of the full `voice-notes-api` execution flow (task run,
not just init) plus the user's repeated corrections converged on a three-layer
model for the agent lifecycle. This session consolidated it into
`docs/AGENT_LIFECYCLE.md` (§0, §1.2, §4.6/4.7, §4.8, §5, §6, §8, design note,
open risks). No feature code shipped; design-only.

**Decisions taken (all confirmed by the user):**
1. **Registration is a mirror of facts.** Nothing is recorded before it happens.
   The `TaskManager` performs the real action (materialize/destroy a worker,
   start/stop polling, open/close queue dispatch); only after confirmation of
   success does the `Runtime` ask the `AgentRegistry` to record the fact.
   Registering a `pool_size` before the workers actually materialized is
   forbidden (would give false information).
2. **`Runtime` is the only layer with initiative and the public face** (CLI/HTTP/
   programmatic, §6): it decides, delegates the fact to the `TaskManager`, and
   records posteriori in the `AgentRegistry`. The above inverts the previous
   "registry declares → taskmanager materializes" into "taskmanager executes →
   runtime records posteriori → registry mirrors".
3. **`AgentRegistry` = posterior mirror + owner of the runtime YAML cache.**
   It owns (a) the live catalog (class/instance/dep state) and (b) the runtime
   cache of YAML specs (§4.7). It never materializes or executes. The spec enters
   the cache only after the class is actually created; it persists across
   `destroy_class` so `recreate_class` works.
4. **`TaskManager` (mini-castor) is the executor of facts, blind to the domain
   and to the registry** — it only knows "run/stop this task", not that a task is
   "the agent lifecycle". All lifecycle mutations become Runtime→TaskManager
   facts recorded posteriori.
5. **Init = build the initial state and the initial cache** (§8). The bootstrap
   constructs the catalog state + initial YAML cache in the registry, posteriori
   to each worker being materialized. It does **not** run business tasks.
6. **disable ≠ destroy at the TaskManager level:** disable closes the queue
   dispatch (workers keep draining, policy A); destroy destroys the workers and
   removes the dispatch (armageddon). disable never kills workers.
7. **Materialization is per-instance and per-state:** only enabled instances get
   a worker; instances of a disabled class exist (to drain/scale) but are born
   disabled; enable_class materializes the born-disabled ones.
8. **No "instance supervisor"** — materialization/scaling is the Runtime's
   orchestration over the TaskManager. Removed the phrase throughout.

**Voice-notes mapping that grounded the model (verified in code):**
- `TaskManager`(castor) = `tasks.py` `manager = Manager(db)` + `@manager.task`
  submit/status + `run_agent_crew_worker` (init as "a task like any other").
- The init is conceptually a task registered *by someone who uses castor* (the
  entrypoint/CLI), not something castor decides on its own — hence the Runtime.
- `AgentFactory`/`create_all_pools` (registry-like) is declarative and does not
  know castor; castor/CLI invokes it. `_run_agents` does `agent.run()` (idle
  polling); `start_voice_note_workflow` deposits the root into the starting
  agent's queue. The executor of the walk (workers) is anonymous/decoupled.
- `SequenceAgent.perform` concretizes its sub-DAG (agents.py:578) — not the
  manager. Any agent may be a starting agent (ARCH §6).

**Docs changed (design, no code shipped):** `docs/AGENT_LIFECYCLE.md` — §0 (five
layers incl. Runtime; registration-is-a-mirror principle), §1.2, §4.7 (YAML cache
owned by registry, posteriori), §4.8 (registry records posteriori; runtime is the
public face; CLI/HTTP rewritten toward Runtime), §5 (per-flow "How" with
Runtime→TaskManager→Registry order and disable≠destroy), §6 (three-layer
responsibilities), §8 (init = build initial state + initial cache), design
note + open risks wording.

**Verification:** docs-only; no code/tests touched this turn. (Run `ruff`/`pytest`
not needed for design-only change; next implementation turn re-runs them.)

**Known issues / open points (for the up-coming TaskManager definition):**
- The `TaskManager` (mini-castor) behavior for the lifecycle (materialize/destroy
  worker, open/close dispatch) is described here only at the conceptual level;
  its concrete task/state surface is the next step to define.
- Registry variations (which queries, cache helper methods) are sketched in §4.8
