## Session 7 — critical corrections to the decoupled polling model

**Context.** Before implementing LEG-025 (worker) / LEG-026 (E2E), a full audit
of the already-shipped modules (via 4 explore subagents) exposed deviations from
`docs/ARCHITECTURE.md` and the approved specs that broke the designed
decoupled/polling model. Maintainer decision (Session 6 journal): fix the
*critical* deviations first, then build LEG-025/026 on the corrected base;
document the non-critical findings as technical debt.

**Critical corrections shipped (all green: 102 tests, ruff check+format,
pyright):**

1. `manager.submit` no longer only creates a task tuple; it now **deposits the
   first `ExecutionRequestMessage` (root step) into the starting agent's queue**
   and stages `payload={"input": payload}` (ARCH §7.1 "synthetic parent stages
   inputs and pushes step one"). Added `agent_queue(agent_id)` as the namespaced
   way the manager reaches an arbitrary agent's queue without knowing the agent.
2. `AgentBase._advance` now **derives the next agent from the DAG in the token**
   (`route_pattern_names[current_index + 1]`), not from a caller-supplied
   `next_agent_id`. `_advance` signature simplified (accidental `next_agent_id`
   param removed).
3. `AgentBase._finish` now **writes `results:{task_id}`** (`{"output": ...}`) on
   root/client-return deliveries, in addition to depositing the
   `ExecutionResultMessage` to the client queue (ARCH §7.7, LEG-053).
4. `AgentBase.process_next` now calls `_heartbeat(handle)` at handle start.
5. `ToolAgent._handle` now decides final-vs-forward by position in the DAG:
   last step -> `_finish`, intermediate step -> `_advance` (previously it always
   `_finish`ed; *never* forwarded).
6. `status` now **derives COMPLETED** from the `results:{task_id}` board entry
   when present (state is board-derived, polling-only; no reader has to mutate
   task state synchronously). Board remains source of truth.
7. `AgentBase` constructor / `ToolAgent` constructor accept the optional
   `results_board`; passed through.

**Tests written (red first then green):**
- `tests/test_flow_integration_decoupled.py` (new): pins the corrected flow end
  to end over the real modules — submit deposits step one in the starting
  agent's queue; a polling `ToolAgent` (which never knows the client/task) runs
  it; root result lands in `results:{task_id}`; `status` reflects COMPLETED with
  output. This is the decoupled base LEG-026 builds on.
- `tests/test_leg023_agentbase.py`: `ChainAgent` no longer carries
  `next_agent_id`; next step is derived from the token DAG (2-step chain across
  two agents still works).
- `tests/test_leg014_manager.py`: `status` COMPLETED assertion strengthened for
  a deposited result.

**Logging added (rule 11, with implementation):**
- `manager submit` emits INFO with `task=<id> owner=<client> starting_agent=<a>`.
- `_finish` root result / tools emit INFO/DEBUG around deposit. Existing agent
  run/lease/dispatch events unchanged.

**Verified decoupled flow (REPL + test):**
```
submit("client-a","transform",{"text":"hello"})
  -> step one enqueued on agent_queue("transform")
  -> ToolAgent.run() polls it          (steps processed = 1)
  -> results:{T-1} = {"output": ...}   (board)
  -> status -> COMPLETED + output
```

**Known issues / open points (documented technical debt — decision needed):**
- Manager task registry (`_SUBSTRATE["tasks"]`) is still an in-memory dict, not
  a `tasks` board (ARCH "everything is a board"). Requires an async refactor of
  `submit`/`status`/`set_task_state`/`Reaper` and does NOT block the corrected
  polling flow. Flagged as debt, not fixed in this pass.
- The generation counter is in-memory (task-id uniqueness). Acceptable as a
  stable-identity concern, not an execution handle.
- ClientPseudoAgent / worker still to be authored to *drain* the `client:{id}`
  queue and mark CLIENT_TERMINATED (LEG-025 worker, LEG-050/053) — status
  currently derives COMPLETED from the results board instead.

2. Implement LEG-026 E2E example on the corrected, decoupled base.

## Session 7 continuation — LEG-025 (worker REST) + LEG-026 (E2E) on the corrected base

**Methodology enforcement.** Maintainer feedback: "don't improvise; implement to
the design and re-audit each shipped spec against the designed architecture so I
don't have to redo the mess." This is now **AGENTS.md rule 12** (a process rule,
not journal content). Work follows contract-first TDD: LEG-025/026 contract
specs (`docs/CONTRACTS/LEG-025-worker-rest.md`, `LEG-026-e2e-example.md`) used as

**LEG-025 — Worker (REST).** Implemented TDD (red first):
- `src/legio/api.py`: `create_app()` FastAPI surface. `POST /submit
  {client_id, agent, payload}` -> `{task_id}` via `manager.submit`; `GET
  /status/{task_id}?client_id=` -> task state + result via `manager.status`,
  ownership enforced. HTTP errors per LEG-016 taxonomy with stable `code`
  (`access_denied` 403, `unknown_task` 404, 422 on bad body) as a top-level
  JSON body.
- `src/legio/worker/__init__.py`: `Worker` — one replica owning one `AgentBase`;
  `process_once()` drains the agent's queue once via `AgentBase.run()`.
  Polling-only, no busy loop (LEG-023); a live replica is scheduled by a
  supervisor/reaper, not a spin.

**LEG-026 — E2E example `transform` (domain-free).** A client submits to the
`transform` agent over REST; a `Worker` replica polls the queue and runs the
registered fake tool; the root result lands in `results:{task_id}` (LEG-053) and
`status` reads it back. Boundary is the REST surface; shared in-process substrate
(one manager/board/queue) as on a single node. Logging observability asserted:
`manager submit`, `agent run`, `worker process`, `agent root result` INFO events
all visible (rule 11, "example visible in logs").

**Re-audit vs design (rule 12).** Confirmed faithful: polling-only API
(client polls status); decoupled (submit -> starting agent queue, worker drains,
DAG routing; no orchestration); results on a board (source of truth); worker
knows only its queue + injected registry, never the task; domain-free fake tool;
ownership-enforced status.
