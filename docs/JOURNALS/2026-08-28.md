**LEG-027 — Auth middleware.** The two-level token stores and `AuthMiddleware`
(substrate-level authorization) already existed and were CLOSED under LEG-017
(`src/legio/security/` + `tests/test_leg017_security.py`). LEG-027 is the
integration: guard the FastAPI `submit`/`status` surface per the LEG-017
endpoint→token map and config shape (`api.clients` with `token`/`agents`).

Implemented TDD (red first; `tests/test_leg027_auth.py` → 9 tests):

- `create_app(clients: ClientTokenStore | None = None)`:
  - **Guarded mode** (store provided): `submit`/`status` require a valid client
    token in `Authorization: Bearer <token>` (401 `unauthorized` otherwise); the
    `client_id` is **derived from the token** (LEG-017 §4 — never trusted from
    the request body); a restricted token may only hit its listed starting
    agents (403 `forbidden`); `status` is readable only with the token that owns
    the task (403 `access_denied` on foreign, via the mini-manager's ownership).
  - **Open mode** (no store): unchanged behavior (`client_id` from request) so
    embedded/unauthenticated contexts and the domain-free E2E example keep
    working.
- `SubmitRequest.client_id` is now optional (guarded mode derives it).
- Bearer-token extraction via `_bearer_token()` (regex on `Authorization`).

**Logging (rule 11):** `api` logs WARNING on unauthorized/forbidden/denied
requests and INFO on submit. Tokens are **never** logged (only
consumer_id/agent) and are absent from responses (asserted).

**Validation case (LEG-027):** the LEG-026 example runs behind auth — a real
`Worker` replicating the domain-free `transform` tool completes a task submitted
with a valid token, `status` returns it (COMPLETED + output), and revocation
blocks a repeat immediately. Both exercised as green tests.

**Re-audit vs LEG-017/architecture (rule 12):** confirmed faithful — two-level
model (client tokens now, federation reserved for R-9); endpoint→token map (§3:
submit/status → client); default-all / restricted-`agents` allowlist (§4);
ownership via the mini-manager; immediate revocation; 401/403 mapping;
no-token-in-logs/responses (§9). Polling-only API preserved; client_id derived
from the token (trusted identity), not the body.

**Verification:** 117 tests pass; `ruff check`, `ruff format --check`,
`pyright src/` all clean.

**Known issues / open points (documented debt, unchanged):** manager task
registry still an in-memory dict (not a `tasks` board) — needs an async refactor
before R-3; federated client-token-guarded surface (LEG-017 §5) only activates
at R-9.

## Session 8 addendum — re-audit of the R-2 implemented set (rule 12)

**Trigger.** The maintainer asked for an explicit verification that everything
shipped so far (the corrected base + LEG-025/026/027) is right and faithful to
`docs/ARCHITECTURE.md`, rather than moving straight to R-3. Re-audited every
module against the architecture and its approved contracts.

**Verified faithful (no change needed):**
- Decoupled polling (ARCH §0/§7): `submit` deposits step-one into the starting
  agent's queue; agents poll their own queue; routing is derived from the DAG in
  the token (`_advance` uses `route_pattern_names[current_index+1]`); no central
  engine, no callbacks. Domain-free (rule 7).
- FlowToken fields + "finality by position" (ARCH §3/§6); root deposits into
  `client:{task_id}` queue and `results:{task_id}` board (ARCH §6/§7, LEG-053).
- ToolAgent frames `input`/`out` per LEG-022 spec (the ARCH §5 blackboard
  `output_as`/`input_mapping` are R-4 refinements).
- `AgentBase._attempts` in-run tracking + simple retry are in LEG-023 scope;
  field-based retry (`next_run_at`/`attempts`) is deferred to R-6 (LEG-061).
- Auth surface (LEG-027) over LEG-017 two-level model (client tokens on
  submit/status, derived client_id, allowlist, ownership, revocation, no-token
  in logs/responses).

**Deviation found and FIXED:**
- ARCH §2/§7.7/§13 ("everything is a board"; `tasks` is an explicit board scope)
  was violated: the mini-manager kept task state in an in-memory dict
  (`_SUBSTRATE["tasks"]`). Refactored to a real `tasks` board (`tasks_board()`,
  scope `tasks`); `submit`, `status`, `set_task_state` and `Reaper` now read/write
  the board. `set_task_state` and `ClientPseudoAgent.handle_termination_request`
  became async (board I/O). Reaper enumerates boards via `stored_keys()`
  (stripping the scope prefix). 117 tests green; ruff, format, pyright clean.

**Documented forward-scoped debt (not defects for R-2, out of issue scope):**
- Coarse `Reaper` (force-terminates all non-terminated client queues; does not
  yet inspect lease expiry/attempts/DLQ) — refined at R-6 (LEG-060/062).
- Input rides the request payload rather than a blackboard frame (satisfies
  LEG-014; ARCH §7.1 "stages inputs" boarding/`input_mapping` refined at R-4).
- `AgentBase._attempts` in-process; retry-as-field at R-6 (LEG-061).

**Next steps**
1. Push the audit/fix + LEG-027 commits; submit #19 (LEG-027) for maintainer
   approval.
2. R-2 now ships on a fully board-backed mini-manager; proceed to R-3 (atomics)
