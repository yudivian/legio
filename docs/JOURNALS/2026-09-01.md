# 2026-09-01 — Session 15h: the manager's store IS a TaskRegistry (concept settled)

## Scope
A conceptual clarifier that UNBLOCKS the item-2 terminology. The maintainer
challenged my invented "kv_store/dict" for the beaver ``tasks`` dict: "first
that must have a reference to the task because it manages it... isn't it a task
registry?" Answer: **yes**. Settled this turn.

## What was settled (decision, final)
- The manager's persistent ``tasks`` dict is a **TaskRegistry**: a record
  ``task_id → {owner, state, token (FlowToken reference), payload}``. `submit`
  writes it; `status` reads it (existence + owner check → PermissionError, and
  base state); the completed output is read from the task's final-result queue
  (Schema 2), not from the registry.
- This is runtime **governance state** — NOT flow state (flow state rides in the
  message ``payload``, built by agents via ``build_payload``). Agents never touch
  the registry; only the manager's `submit`/`status` do.
- Therefore **no "Board" term is needed anywhere**: what v1 called
  ``tasks_board()`` is the **TaskRegistry**; the ``results`` "board" is gone
  (results live on the final-result queue); ``gates`` is a class-enable registry.
  My earlier "kv_store/dict store" proposal is retracted — it was a leftover of
  inherited "board" naming, not a real need.
- The FlowToken reference in the registry is what the manager manages: a task
  is represented by its token (root), matching Schema 2 (the token is the task's
  identity through the flow).
