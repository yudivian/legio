# LEG-042 — Fan-in: gathering queue by (parallel, task) identity

- **Status:** DRAFT (awaiting maintainer approval)
- **Rasante:** R-4
- **GitHub issue:** #25
- **Source:** `docs/PLAN.md` (LEG-042)
- **Depends on:** LEG-023, `docs/AGENT_LIFECYCLE.md` §12

## Goal

The parallel fan-in (per-class **gathering queue**, bookkeeping
`state:parallel:<class>`, AGENT_LIFECYCLE §12.4): join the return of every
branch of a task exactly once, in a slot-stable way (each branch has a fixed
slot from fan-out, even before it returns), and behave correctly — never
silently — when a branch is bugged or missing. Sequence is forward-only and has
no fan-in (§12.3).

## Scope

- **In scope:** gathering structure, join slot stability, exactly-once join,
  visible failure when a branch never returns.
- **Out of scope:** agent-level behavior (sequence/parallel agents on top).

## Contract & design

- The payload travels **in the messages** (AGENT_LIFECYCLE §12.1);
  the gathering queue of the parallel class holds the children's
  `ExecutionResultMessage` returns from which the parallel **builds its
  payload** — there is **no** out-of-message accumulator and no central store.
- The parallel's bookkeeping (`state:parallel:<class>`, keyed per task) records
  the continuation and one slot per branch, each slot pre-created at fan-out and
  filled when that branch's result returns; the join completes when every slot
  of the task is filled.
- Dedupe per **(parallel, task, branch slot)** — enforced by bookkeeping keyed
  directly on the constant `task_id` (the same across the whole fan-out, LEG-041)
  and by slot identity from the result's `branch_id` (autogenerated by the
  parallel at fan-out): two branches — even two that are the very same
  class/sequence — are two distinct slots; no join by agent name.
- **Join→advance ordering (crash-safe).** The advance deposit happens before
  the join row is deleted (advance-then-delete): a crash that lands between the
  two leaves a stale join row rather than orphaning the parent route.

## Interface

- Gathering-queue composition API; step join resolution API.

## Acceptance criteria

From `docs/PLAN.md` (LEG-042), verbatim:
- Two branches of one parallel task join exactly once each; a missing/bugged
  branch result is surfaced visibly, never silently; join slots are stable from
  fan-out (slot-stable even before a branch returns).

## Tests

- Contract tests (red first): slot-stability pre-arrival, exactly-once join,
  visible failure for a missing branch.
